Sentry Review 2026: Complete Guide to Error Tracking for Your Apps

Sentry is one of those tools that most developers have heard of long before they ever use it. It's the default answer when someone asks "how do I find out what's breaking in production?" But default answers deserve scrutiny, especially when the pricing page has grown more complicated every year and the feature list now includes tracing, session replay, profiling, cron monitoring, and an AI debugging agent.

I've been running Sentry across a handful of projects for the better part of a year — a Next.js SaaS app, a Django API, a small React Native app, and a self-hosted instance for a client with strict data rules. This review covers what actually works, what gets in your way, and whether it's still the right pick in 2026.

What Sentry Actually Is

Sentry started in 2008 as an open-source error tracker for Django and has quietly turned into a full application monitoring platform. The core product is still error tracking: an SDK in your app catches exceptions, captures a stack trace, attaches context, and ships it to Sentry's servers. Sentry groups similar events into issues, alerts you, and gives you enough context to reproduce and fix the bug.

Around that core, Sentry has bolted on:

  • Performance monitoring (distributed tracing via spans)
  • Session Replay (video-like recordings of user sessions tied to errors)
  • Profiling (continuous CPU profiling with flame graphs)
  • Cron monitoring (dead-man's-switch alerts for scheduled jobs)
  • Uptime monitoring (endpoint checks, added more recently)
  • Seer (an AI agent that suggests root causes and fixes)

All of it feeds into one dashboard, which is either the product's biggest strength or its biggest annoyance depending on how much you enjoy dense UIs. More on that later.

The SDK coverage is genuinely impressive — over 100 platforms and frameworks, including JavaScript, Python, Go, Rust, Ruby, PHP, Java, .NET, Swift, Kotlin, Flutter, React Native, and a long tail of frameworks like Laravel, Django, Rails, Spring, and Next.js. If you're building something mainstream, there's an official SDK. If you're building something odd, there's probably a community one.

Feature Breakdown

Error tracking and grouping

This is where Sentry still earns its reputation. Out of the box, an SDK captures unhandled exceptions, unhandled promise rejections, and — if you wire it up — manually reported errors via Sentry.captureException(). Each event arrives with a stack trace, request data, browser or device info, release version, and breadcrumbs.

Breadcrumbs are the feature I underappreciate until I need them. Sentry records a rolling log of the last ~100 things that happened before the error: HTTP requests, console logs, navigation events, database queries. When a user reports "the checkout button did nothing," the breadcrumb trail usually tells you whether it was a failed API call, a JS error swallowed by a try/catch, or a rage click on a disabled element.

Grouping works well by default. Sentry fingerprints events by stack trace and error message, so 40,000 occurrences of the same bug collapse into one issue with a count and an affected-user total. When it gets it wrong — and it does, especially with errors that include dynamic strings in the message — you can merge issues manually or set custom fingerprints in the SDK.

For JavaScript specifically, source map handling is the standout. Upload them via the CLI, a bundler plugin (webpack, Vite, Vite/Rollup, esbuild all have official integrations), or CI, and Sentry maps minified production stack traces back to your original source. It also handles the "source maps uploaded but the release doesn't match" problem better than it used to, though you'll still hit it if your deploy pipeline isn't disciplined.

For native apps, Sentry does symbolication for iOS (dSYM) and Android (ProGuard/R8 mapping files) with the same upload-then-associate-with-release model. It's the part of Sentry that most often goes wrong in my experience — a missing dSYM upload means a stack trace full of hex addresses — but the tooling to diagnose it (release details page, "missing symbols" warnings) is clear enough that you can fix it in an afternoon.

Context and debugging tools

Beyond the stack trace, Sentry attaches:

  • Tags — environment, release, server name, custom key-values for filtering
  • User context — ID, email, IP (with PII scrubbing options)
  • Custom context — arbitrary structured data you attach to events
  • Attachments — log files or screenshots, within quota limits
  • Suspect commits — Sentry correlates a new issue with recent commits to your repo and flags the commit most likely to have introduced it
  • Stack trace linking — click a frame and jump straight to that line in GitHub, GitLab, or Bitbucket

Suspect commits are hit-or-miss. When they work, they save real time. When your commit messages are "fix stuff" and your releases aren't tagged cleanly, they're noise. The feature is only as good as your release hygiene.

Performance monitoring

Sentry's tracing model is span-based. You instrument your app (automatic instrumentation covers most frameworks; manual spans fill in the gaps), and Sentry assembles traces across services. You get p50/p75/p95/p99 latency, throughput, error rates, and — usefully — detection of N+1 database queries and slow spans.

Web Vitals support (LCP, FID/INP, CLS) is built in for frontend projects. For backend services, the span waterfall view is the thing you'll actually use: it shows exactly which database call or external API ate 800ms of a 1.2s request.

The catch is cost. Tracing is billed per span, and a moderately busy API can generate enormous span volume. Sampling helps, but Sentry's default sampling and quota model takes some getting used to. More on that in the cons.

Session Replay

Session Replay records DOM mutations, Mouse movements, clicks, and console output, then lets you scrub through a session like a video. The genuinely useful part is the linkage: when an error fires during a replay, Sentry jumps to that exact moment and shows you the stack trace alongside what the user was doing.

Privacy controls are solid. You can mask all text by default, block specific elements or selectors, and exclude entire routes. The default configuration masks text inputs and blocks media, which is the right default. Replays are sampled — by default only a fraction of sessions, plus 100% of sessions with errors — which keeps volume sane.

The limitation: replay captures are large. A 30-minute session with heavy DOM churn can be several megabytes. Sentry's quota is measured in replays, not bytes, but the network cost on the client is real for users on slow connections.

Profiling

Continuous profiling attaches to your backend services and produces flame graphs tied to traces. If you're debugging "why is this endpoint slow when the database looks fine," the flame graph is where you find the answer — a serialization loop, a regex catastrophe, a lock contention issue.

It's available on the Business plan and above. On smaller plans you get limited or no profiling, which is a reasonable line to draw since profiling is expensive to store.

Cron monitoring and uptime

Cron monitoring is one of those features you don't think you need until a nightly job silently stops running for two weeks. You register a Monitor, your job pings Sentry on start and finish, and Sentry alerts you if a check-in doesn't arrive on schedule. It supports timezone-aware schedules and grace periods.

Uptime monitoring does simple HTTP checks against endpoints with configurable intervals. It's not a replacement for a dedicated uptime service like Better Stack or Checkly — the check frequency and alerting options are more basic — but if you're already in Sentry, it's convenient to have.

Alerts and integrations

Alerting is flexible without being overwhelming. You can alert on issue frequency thresholds, on new issues, on user impact counts, on performance metric regressions, and on cron check-in failures. Anomaly detection (alert when an issue spikes relative to its historical baseline) is available on higher tiers and works well for catching regressions that don't cross a static threshold.

Integrations cover the usual suspects: Slack, Microsoft Teams, Discord, Jira, Linear, GitHub, GitLab, PagerDuty, Opsgenie, and a long tail. The Slack integration is the one most teams live in — you get an issue card with a stack trace preview and buttons to resolve, ignore, or assign.

Seer (AI debugging)

Seer is Sentry's AI layer. Point it at an issue and it analyzes the stack trace, the surrounding code from your repo, and the breadcrumbs to suggest a root cause and sometimes a patch. It's available on paid plans with usage limits.
