Playwright Review 2026: The Testing Framework That's Taking Over

Five years ago, if you asked a room of developers what they used for end-to-end testing, you'd hear "Cypress" and "Selenium" and not much else. Ask that same question in 2026 and the answer has shifted hard. Playwright went from a curious Microsoft side project to the default choice for a lot of teams, and the numbers back it up: it's the most-used browser automation library on npm, and job listings mentioning it have roughly tripled since 2023.

But popularity isn't the same thing as being right for your project. I've been running Playwright in production suites for the last few years — small indie apps, a mid-sized SaaS with 900+ tests, and a couple of client projects where I had to migrate away from Cypress. This review covers what actually works, where it gets annoying, and whether you should move.

What Playwright Actually Is

Playwright is an open-source browser automation and testing framework, originally built by a team at Microsoft (several of whom worked on Puppeteer at Google). It's licensed under Apache 2.0, which means the core tool is free — no per-seat licensing, no test-minute metering, no sales call.

The thing that separates it from most competitors is breadth. One API drives Chromium, Firefox, and WebKit (the engine behind Safari). Not emulated Safari — actual WebKit. That matters more than people realize, because Safari bugs are the ones that sneak through to production when your test suite only runs on Chrome.

You can write tests in TypeScript/JavaScript, Python, Java, or .NET. The test runner ships in the box, so you don't need Jest, Mocha, or a third-party runner bolted on top. And it handles more than just clicking buttons in a browser — you get API request testing, component testing, and mobile viewport emulation from the same library.

Feature Breakdown

Auto-waiting and web-first assertions

This is the feature that converts people. In older frameworks, you spent half your test code writing waitForElement, sleep(2000), and retry loops. Playwright's locators check whether an element is visible, stable, enabled, and actually receiving events before interacting with it. If it isn't ready, it retries.

Web-first assertions work the same way. Instead of:

expect(await page.textContent('.status')).toBe('Done');

you write:

await expect(page.locator('.status')).toHaveText('Done');

That second version retries until it passes or times out. It sounds like a small thing. In practice it removes the single biggest source of flaky tests, and it's the reason migrations from Selenium tend to shrink test suites by 30–50% in line count.

Browser contexts for isolation

Playwright can spin up a fresh browser context — think of it as an incognito window with its own cookies, localStorage, and cache — in milliseconds. Because contexts are cheap, every test gets a clean slate without the overhead of launching a new browser. Run them in parallel and a 500-test suite that took 20 minutes on Selenium finishes in three or four.

Trace Viewer

When a test fails in CI and you weren't watching, the Trace Viewer is what saves you. It records a full timeline: DOM snapshots at every step, network requests, console logs, and a filmstrip of screenshots. You scrub through it like a video and see exactly what the page looked like when the assertion failed.

I've debugged failures that would have taken an hour of local reproduction in about ninety seconds with a trace file. It's the feature I'd fight hardest to keep.

Codegen

npx playwright codegen https://yoursite.com opens a browser and records your clicks into test code. It's not going to write your whole suite, but it's genuinely useful for scaffolding selectors and getting past the blank-page problem. The selector it picks is usually a resilient one based on role and accessible name, not a brittle CSS path.

UI Mode

npx playwright test --ui gives you a watch-mode interface with a test tree, time-travel debugging, and a locator picker. It's the closest thing to Cypress's developer experience, and it closed a gap that used to be a real reason to pick Cypress.

Network interception

page.route() lets you mock API responses, throttle connections, or block third-party scripts. This is how you test error states — a 500 from your billing endpoint, a slow network on mobile — without touching your backend.

Auth state reuse

You can log in once, save the storage state to a file, and reuse it across hundreds of tests. No repeated login flows eating 40 seconds each. This alone cut our suite runtime by about 25%.

Playwright Agents and MCP

Newer additions worth knowing about: Playwright ships an MCP server so AI coding assistants can drive a browser, and the team has been building "agents" that help generate and repair tests. It's early, and I wouldn't trust it to write your critical-path tests unsupervised, but for scaffolding and healing broken selectors it's already useful.

For a solo dev or small team, the honest answer is that you probably don't need any of these. GitHub Actions gives you free minutes on public repos and generous limits on private ones, and Playwright's built-in sharding splits your suite across parallel runners without extra tooling. I ran a 900-test suite on GitHub Actions for months and paid nothing.

Pros and Cons

What I like

Genuinely fast and parallel out of the box. Free sharding and worker parallelism means you don't hit a paywall the moment your suite grows.

Real WebKit support. If your users are on Safari — and on mobile, they are — this is the difference between catching a bug in CI and hearing about it from a customer.

Trace Viewer is best-in-class. Nothing else in this price range gives you DOM snapshots, network, and console in a single scrubbable timeline.

Multi-language. Your backend team writing Python can contribute tests without learning the JS ecosystem.

Strong documentation. The docs are searchable, versioned, and full of runnable examples. That's rarer than it should be.

MCP and AI tooling. Playwright is ahead of the curve on letting AI assistants drive a browser, which is quietly becoming a real workflow.

What I don't like

The API surface is big. Playwright has a lot of ways to do the same thing — page.$, locator(), getByRole(), raw selectors. New team members write inconsistent tests until someone sets conventions. Cypress's smaller API is easier to standardize on.

Component testing is still not there. It's marked experimental, and it shows. If component testing is central to your strategy, Cypress or Vitest is a better fit today.

Test isolation requires discipline. Because contexts are cheap, it's tempting to share state between tests. Do that and you get order-dependent flakiness that's miserable to debug. The framework won't stop you.

Debugging in headed mode can be slow. Launching a real browser with a visible window for local iteration isn't as snappy as Cypress's in-browser runner.

No built-in dashboard. The HTML reporter is decent, but for historical trends and flake tracking you'll need Currents, Checkly, or something similar. Cypress bundles this (behind a paywall).

Migration isn't free. Moving a large Cypress suite takes real work. The APIs are different enough that it's a rewrite, not a find-and-replace.

Who Should Use Playwright

Pick Playwright if: you need cross-browser coverage including Safari, you want free parallelization, your team writes in more than one language, or you're starting a new test suite from scratch in 2026. For most teams building web apps today, it's the default.

Stick with Cypress if: you're a small JS-only team with a suite that works, you lean heavily on component testing, or you value the in-browser debugging experience enough to pay for parallel runs.

Stay on Selenium if: you're maintaining a legacy suite that isn't worth rewriting, or you need browser support Playwright doesn't offer.

Final Verdict

Playwright is the best general-purpose browser testing framework available right now, and it isn't particularly close for new projects. The combination of free parallelization, real WebKit support, and the Trace Viewer covers the three problems that Make E2E testing painful — speed, coverage, and debuggability — without asking you to pay for any of them.

It's not perfect. The API is sprawling, component testing is immature, and you'll want a third-party service eventually for reporting at scale. But those are gaps at the edges, not problems at the core.

Rating: 4.6 / 5

If you're starting fresh, use Playwright. If you're on Cypress and your suite is under 200 tests, the migration is worth it. If you're on Cypress with 800 tests and it's working, don't fix what isn't broken.

FAQ

Is Playwright free?

Yes. The core framework is open source under Apache 2.0 and costs nothing, including parallel execution and sharding. You only pay if you use a cloud device farm, a managed execution service, or a reporting product on top of it.

Playwright vs Cypress — which is better in 2026?

Playwright for most teams. It supports more browsers properly, parallelizes for free, and handles multi-tab and multi-origin scenarios that Cypress struggles with. Cypress still has a nicer onboarding experience and more mature component testing, so it's a reasonable pick for a small JS-only team.

Does Playwright replace Selenium?

For new projects, generally yes. Playwright's auto-waiting removes most of the boilerplate Selenium requires, and the built-in test runner means fewer moving
