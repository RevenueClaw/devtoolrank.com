NGINX Review 2026: Is It Still the King of Web Servers?

NGINX turned 22 this year. It has been the most-used web server on the internet for over a decade, and nothing in 2025 or 2026 has seriously threatened that position. But "most used" and "best choice for your project" are different questions, and the gap between them has widened.

Here's the honest setup: NGINX Open Source is still the safest default for serving static files and terminating TLS in front of an application. NGINX Plus, the commercial product, is a harder sell than it was five years ago, because a lot of what used to justify the license fee now exists in cheaper or free alternatives. And the Kubernetes story — long one of NGINX's strongest cards — got genuinely messy when the community Ingress controller was put out to pasture.

This review walks through what NGINX actually does well in 2026, where it still frustrates people, what it costs, and whether you should pick it over Caddy, Traefik, Apache, or HAProxy.

What "NGINX" means in 2026

The name covers a lot of products now, and reviews often blur them together. Worth separating:

  • NGINX Open Source — the original. BSD-2-Clause licensed, free, maintained by F5 with community contributions. This is what most people mean when they say NGINX.
  • NGINX Plus — the commercial subscription. Adds active health checks, a dynamic reconfiguration API, a live activity monitoring dashboard, JWT and OIDC support, session persistence, and vendor support.
  • NGINX Unit — a separate application server that runs Python, PHP, Node.js, Go, Java, and Ruby apps. Free, with a Plus tier for commercial support. It competes with Gunicorn/uWSGI/Puma rather than with NGINX itself.
  • NGINX App Protect — the WAF and DoS protection line, sold as an add-on.
  • NGINX Ingress Controller — F5's commercial/OSS Kubernetes ingress. Distinct from ingress-nginx, the community controller, which the Kubernetes SIG Network announced would be retired in March 2026. If you're still running ingress-nginx in production, that migration is your problem this year, not next.
  • NGINX Gateway Fabric — the Gateway API implementation, which is where F5 is steering Kubernetes users long-term.

There's also freenginx, the fork Maxim Dounin announced in early 2024 after a dispute over how F5 handled security disclosure. It hasn't taken meaningful market share, but it's a useful signal: the governance of the open source project is not universally uncontested.

Architecture and throughput

NGINX's core design hasn't changed, because it didn't need to. A master process manages a pool of worker processes, each running an event loop (epoll on Linux, kqueue on BSD/macOS). One worker can hold tens of thousands of idle connections without spawning a thread per request.

The practical consequence is memory predictability. A default NGINX install idles in the low single-digit megabytes per worker. Under a slow-client load — lots of connections, little data — it barely moves, because it buffers requests and responses rather than tying up a backend process. That's the same reason it's a good reverse proxy: a slow mobile client on a 3G connection doesn't hold an application worker hostage.

Tuning is still a handful of directives. worker_processes auto; to match CPU cores, worker_connections sized against your file descriptor limit, sendfile on; and tcp_nopush on; for static file serving. There is no config file generator, no GUI, and no autotuning. You set it or you don't.

Reverse proxy and load balancing

This is where NGINX earns its keep. Out of the box you get:

  • Round-robin, least-connections, IP hash, and generic hash load balancing
  • Weighted backends and backup servers
  • Passive health checks (max_fails, fail_timeout) in Open Source
  • Active health checks only in Plus
  • Connection limiting (limit_conn) and request rate limiting (limit_req) with burst and nodelay handling
  • Request/response buffering, header rewriting, and proxy_cache with disk or memory storage
  • Upstream keepalive connection pools, which matter more than most people realize for latency

The limit_req directive is the one that trips people up most. Without nodelay, requests over the rate are queued and served slowly rather than rejected, which looks like a latency problem instead of a rate-limit problem. It's a two-word fix that people spend an afternoon finding.

The bigger structural limitation: in Open Source, changing an upstream server list requires a config reload. Reloads are graceful — NGINX spins up new workers and drains old ones without dropping connections — but they're still a config write plus a signal, which is awkward if your backend IPs change every few minutes. Plus solves this with a REST API that mutates upstreams at runtime. In 2026, that's the single most defensible reason to pay for Plus.

TLS, HTTP/2, and HTTP/3

TLS termination is solid: SNI, OCSP stapling, session caching, TLS 1.3, and per-server certificate configuration. HTTP/2 has been stable for years. HTTP/3 over QUIC has been available since the 1.25 series and is now generally usable, though you should test it against your CDN and load balancer path before enabling it broadly.

The gap that hasn't closed: NGINX does not issue or renew certificates for you. You wire up Certbot with the nginx plugin, or acme.sh, or a Plus-side njs script. Caddy does this natively with zero configuration. For a solo developer running three sites, that difference is a real chunk of ongoing maintenance.
