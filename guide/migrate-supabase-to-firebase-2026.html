Migrating from Supabase to Firebase in 2026: The Step-by-Step Switch Guide

Almost every migration post you'll read goes the other direction. Firebase to Supabase is the popular move — people get tired of per-read billing, they want SQL, they want their data in a Postgres dump they can actually read. So if you're going Supabase → Firebase, you probably have a specific reason. Maybe you're shipping a React Native app and want Firestore's offline cache without writing it yourself. Maybe your company just signed a Google Cloud agreement and Firebase is the path of least resistance. Maybe you inherited a Supabase project and your team already knows Firebase cold.

Before the walkthrough, read our full Supabase vs Firebase comparison for the head-to-head that motivates this switch.

Those are all legitimate reasons. This guide assumes you have one, and it walks through the migration in the order you should actually do it — with the parts that will break, the parts that cost money, and the parts where you should stop and reconsider.

One thing before we start: this migration is harder than the reverse. Postgres to Firestore means giving up joins, transactions across collections, and SQL constraints. You're not just moving hosting providers. You're changing your data model. Budget a week for a small app, and don't trust anyone who says it's a weekend job.

What actually changes when you move

Let's be concrete about what you're trading, because the marketing pages on both sides are unhelpfully vague.

Database. Supabase gives you Postgres. Real Postgres — foreign keys, views, triggers, pgvector, jsonb indexes, the whole thing. Firebase gives you Firestore, a document store, or Realtime Database if you're feeling nostalgic. Firestore has no joins. You denormalize, or you do multiple round trips, or you duplicate data and write Cloud Functions to keep the copies in sync. Every one of those is a real pattern with real costs. If your Supabase schema has more than two or three joins in any hot query, this step alone should Make you pause.

Auth. Both handle email/password, OAuth providers, and magic links. Supabase's user table is just a Postgres table, which means you can query it, join to it, and write triggers on it. Firebase Auth users are opaque — you get them through the Admin SDK, and you can't write a SQL join against them. That's a real architectural change for apps that store user metadata in the same table.

Storage. Supabase Storage sits on S3 with signed URLs. Firebase Storage sits on Google Cloud Storage with security rules. Both fine. The migration is mechanical, but the URL format changes, so every hardcoded image URL in your app or database has to be rewritten.

Realtime. This is where Firebase is genuinely better and it's not close. Firestore's onSnapshot listeners handle reconnection, offline queuing, and conflict resolution out of the box. Supabase Realtime is good, but you often end up writing the client-side reconciliation yourself.

Functions. Supabase Edge Functions are Deno. Firebase Cloud Functions are Node (and there's a Python runtime now). If you have 15 edge functions, this is a rewrite, not a port.

Hosting. Supabase doesn't host your frontend. Firebase Hosting does, with a global CDN and preview channels per PR. If you were on Vercel plus Supabase, you can consolidate to one vendor here. That's a genuine simplification.

The migration, step by step

Step 1: Audit what you actually use

Before touching anything, inventory your project. Export your schema, list every edge function, count your storage buckets, and grep your codebase for every supabase.from() call. I've watched people start a migration convinced they use four tables, then discover a user_settings table that seventeen components hit.

Also check your Supabase dashboard's usage graphs. If you're on Pro and nowhere near the 8 GB database or 100 GB bandwidth limits, you're on a flat $25/month with no surprises. That's a hard thing to walk away from, and it's worth writing down what you're gaining before you give it up.

Step 2: Design the Firestore data model

Do this on paper first. Seriously — sketch the collections before you write a single line of migration code.

The mental shift: in Postgres you ask "what's the normalized shape?" In Firestore you ask "what does the screen need, and how many reads does it take to get there?" A three-table join becomes either a denormalized document with duplicated fields, or three reads stitched together in the client.

Two rules that save a lot of pain:

  • Subcollections for anything that grows. Order line items belong in orders/{id}/items, not an array on the order document. Documents have a 1 MB limit.
  • Never put high-churn counters on a hot document. Firestore writes to a document are limited to roughly one per second sustained. If you have a post_likes counter getting hammered, you need a distributed counter pattern.

Step 3: Create the Firebase project and pick your plan

You'll start on Spark ($0, no-cost daily limits, hard caps — nothing bills). But you'll almost certainly need Blaze to do the migration itself, because the Admin SDK writes and Cloud Functions both require it. Blaze is pay-as-you-go with no fixed monthly fee; the budget alarm is your friend, and I'll get to that below.

Do not skip the budget alert. Set it at $25 for the first month so you notice quickly if a migration loop is writing documents in a hot cycle.

Step 4: Migrate auth users (the step that goes wrong)

Password hashes are the trap. Supabase's auth service stores bcrypt hashes. Firebase has an import tool that accepts pre-hashed credentials, and bcrypt is among the formats it can take — but the parameters have to line up exactly, and this is the single step where guessing produces a silent security problem.

Verify the current supported hash formats and parameter requirements against Firebase's Admin SDK docs before you run anything at scale. Then test with one user account on a staging project before you touch production.

If the parameters don't line up, you have two fallbacks: force a password reset on next login for everyone (annoying but honest), or keep Supabase Auth running alongside Firebase Auth for a transition period and migrate users lazily as they log in. The lazy approach is more work but it's the one that doesn't generate support tickets.

Also export your auth.users table first — Supabase lets you do this from the dashboard or via pg_dump. You want that backup regardless of what happens next.

Step 5: Move the data

Write a script, don't do this by hand. The shape:

  • pg_dump your Postgres database to CSV or JSON.
  • Run a Node script using firebase-admin that reads the export and writes documents in batches (500 per writeBatch call, or use BulkWriter for larger jobs).
  • For tables with foreign keys, resolve parent IDs first and stash a Postgres-ID → Firestore-doc-ID map, then walk the children.

Two things that will bite you: Postgres timestamp with time zone values need to become Firestore Timestamp objects (not strings, unless you want range queries to fail), and uuid primary keys work fine as document IDs but you lose the ordinal guarantee you had with bigserial — if anything relies on insertion order, add an explicit createdAt field.

Run it against a staging Firebase project first. Then run it twice against production — once as a dry run, once for real — and diff the document counts per collection.

Step 6: Convert RLS policies to Security Rules

Your Row Level Security policies don't have a Firestore equivalent. You rewrite them as Security Rules, and the model is different: Firestore rules evaluate per-document, they can't do joins, and they can't call out to other collections cheaply.

A typical Supabase policy like "users can read their own rows" becomes something like a rule checking request.auth.uid == resource.data.ownerId. Anything that depended on a memberships table to decide access becomes either a denormalized members array on the parent document or a custom claim in the auth token. Custom claims are the better answer for anything role-based — set them with a Cloud Function and read them in rules as request.auth.token.role.

Rules are also where you enforce your data shape, since you're losing Postgres constraints. Validate field types and required keys in the rules themselves, or every client is free to write garbage.

Step 7: Rewrite edge functions

Deno to Node. This is grunt work. The parts that need care:

  • Any function that called supabase.rpc() for a stored procedure needs that logic reimplemented in TypeScript.
  • Functions that touched multiple tables in a transaction become Firestore transactions or batched writes, and Firestore transactions have their own retry semantics.
  • Trigger-based functions (on user insert) map to Firebase's onDocumentCreated. Same idea, different signature.

Step-by-Step Migration

1) Audit Supabase schema and export via pg_dump. 2) Map Postgres tables to Firestore collections or Cloud SQL. 3) Rewrite auth (Supabase Auth -> Firebase Auth). 4) Move storage objects to Cloud Storage. 5) Repoint realtime subscriptions. 6) Run both stacks briefly; cut over on a quiet traffic day.

FAQ

Q: How much is Supabase Pro in 2026?

A: $25/month flat, including $10/month of compute credits — verified on Supabase's pricing page in November 2026.

Q: Is Firebase cheaper?

A: At low steady usage yes; under bursty read traffic Firestore bills can exceed Supabase's flat $25.

The 2-Year Renewal Math (2026 Prices)

Supabase Pro: $25 x 24 = $600 over 24 months — flat, predictable, no year-two jump. Firebase Blaze at a typical small-app usage of ~$25/month: ~$600, but with no ceiling and no floor — a runaway Firestore query can push a month to $100+. The renewal risk here is usage risk, not a price hike.

Note: this is a hosting-style annual-renewal market — promo entry prices are real, but the renewal rate is the number that matters over 24 months.

Verdict

Supabase for predictable flat pricing and real Postgres; Firebase for deep Google-ecosystem integration — migrate only if your usage pattern is flat or you're bought into Google's SDKs.

Check current Supabase pricing (Pro is $25/mo flat) and your current Blaze bill before you commit to either direction.
